# SUMO QUEST 実行計画

## 1. 本書の目的

本書は、`sumo-quest-prd.md`（何を作るか）と `sumo-quest-design.md`（どう作るか）を受けて、**いつ・どの順序で・何を完了とみなして進めるか**を定める。設計書「19. 実装フェーズ」を、担当者が着手できる粒度のタスクへ分解したものであり、設計判断そのものは設計書を正とする。

対象範囲はMVP（設計書「20. MVP受け入れ条件」）までとする。

## 2. 前提と制約

| 項目 | 内容 |
|---|---|
| 配信先 | GitHub Pages（リポジトリ配下のサブパス） |
| サーバー | 使用しない。API Routes / Server Actions / DB なし |
| 保存先 | ブラウザの localStorage のみ |
| 主要技術 | Next.js（App Router）／React／TypeScript／Static Export |
| 状態管理 | React Context + useReducer（ライブラリ導入なし） |
| 対応端末 | 320px幅以上のスマートフォン、タッチ、キーボード |

### この計画の進め方の原則

1. **縦切りを最優先する。** STAGE 1で「開始→学習→取組→報酬→保存→再開」を先に完成させる。6ステージを並行して作らない。
2. **仕組みが先、コンテンツが後。** 汎用化された画面が動いてから、残りステージをデータ追加で増やす。
3. **各フェーズの終わりに必ず本番URLで確認する。** ローカルで動いてもGitHub Pagesのサブパスで壊れる不具合は最後に出ると高コストになる。
4. **相撲コンテンツの正確性は実装と別レーンで進める。** 実装を待たずに文章を用意し、実装完了時点で差し替えられる状態にしておく。

## 3. フェーズ全体像

```text
Phase 0  土台
   ↓        ← 完了ゲート: 空ページがGitHub Pagesで表示される
Phase 1  STAGE 1 縦切り
   ↓        ← 完了ゲート: 1ステージ分のループが本番URLで通る（最重要ゲート）
Phase 2  データ駆動化 + STAGE 2〜5
   ↓        ← 完了ゲート: 5ステージがデータ追加のみで成立する
Phase 3  最終ステージとエンディング
   ↓        ← 完了ゲート: 横綱到達まで通しでプレイできる
Phase 4  品質向上
            ← 完了ゲート: MVP受け入れ条件を全て満たす
```

各フェーズは**前フェーズの完了ゲートを通過してから着手する**。ただしコンテンツ執筆（レーンC）と素材制作（レーンD）は、Phase 0開始と同時に並行で走らせる。

### 並行レーン

| レーン | 内容 | 開始時期 |
|---|---|---|
| A：実装 | Phase 0〜4のタスク | 直列 |
| B：配信基盤 | next.config、GitHub Actions、Pages設定 | Phase 0 |
| C：コンテンツ執筆 | 会話文、クイズ、用語・技の説明 | Phase 0と同時 |
| D：ピクセル素材 | NPC、マップ、技アイコン | Phase 0と同時（暫定素材で先行可） |

レーンCとDの遅れが実装を止めないよう、**プレースホルダ（仮テキスト・単色矩形）で先に実装を通し、後から差し替える**方針とする。

## 4. Phase 0：土台

**目的：** 空のページがGitHub Pages上に表示され、以降のタスクが「アプリの中身」だけに集中できる状態を作る。

### タスク

| ID | タスク | 完了条件 |
|---|---|---|
| P0-1 | Next.js（App Router）+ TypeScript でプロジェクト初期化 | `npm run dev` でトップページが表示される |
| P0-2 | Lint / フォーマット / テストランナー導入 | `npm run lint`、テストコマンドが成功する |
| P0-3 | `next.config.ts` に静的エクスポートと `basePath` を設定 | `npm run build` で `out/` が生成される |
| P0-4 | GitHub Actions ワークフロー作成、Pages有効化 | mainへのpushで自動配信される |
| P0-5 | 型定義 `src/types/game.ts` を作成 | 設計書「8. データモデル」の型が揃う |
| P0-6 | コンテンツデータの空ファイル雛形を作成 | `src/data/` 配下7ファイルが型付きで存在する |
| P0-7 | デザイントークン（色・余白・フォント）を `globals.css` に定義 | 限定色数のパレットが変数化されている |
| P0-8 | `GameShell` / `PixelWindow` / `PixelButton` を実装 | ダミーページでRPG風の枠と押せるボタンが出る |
| P0-9 | `basePath` を考慮した画像パスヘルパーを実装 | ローカルと本番の双方で画像が表示される |

### 完了ゲート

- GitHub PagesのURLで、ピクセル調の枠とボタンを持つダミーページが表示される。
- そのページ内の画像とリンクがサブパス配下で壊れていない。

### 注意点

`basePath` 起因のリンク切れ・画像切れは、この時点で確実に潰しておく。Phase 1以降に持ち越すと、原因の切り分けコストが跳ね上がる。

## 5. Phase 1：STAGE 1 縦切り（最重要）

**目的：** すもう部屋の1ステージだけで、ゲームループ全体を成立させる。ここが通れば残りは拡張作業になる。

### 5.1 保存と進行ルール（先に作る）

| ID | タスク | 完了条件 |
|---|---|---|
| P1-1 | `lib/storage.ts`：localStorageの読み書きと `SaveEnvelope` 対応 | 保存・読込・キー不在の3経路が動く |
| P1-2 | `lib/validation.ts`：セーブデータ検証 | 不正JSON・必須項目欠落を検知し、**データを消さずに**異常を返す |
| P1-3 | `lib/ranks.ts`：累積EXPから番付を導出 | 全10段階の境界値で正しい番付が返る |
| P1-4 | `lib/game.ts`：ステージ解放、学習完了、クイズ結果、クリア判定 | 純粋関数として単体テストが通る |
| P1-5 | `GameProvider` + `useReducer`：8アクションを実装 | Reducerが純粋関数であり、保存は副作用側に分離されている |
| P1-6 | `hooks/useGame.ts` と導出セレクタ | 次の番付までのEXP等が保存値を増やさず取得できる |

**先に単体テストを書く対象**（設計書「17. テスト設計」より）：EXP→番付の変換、横綱条件、ステージ解放順、初回報酬の二重取得防止、セーブ検証、合格率の境界値。これらは画面がなくても検証でき、後から作ると必ず後回しになるためこの時点で書く。

### 5.2 画面

| ID | タスク | 完了条件 |
|---|---|---|
| P1-7 | タイトル画面 | セーブ有無で「つづきから」の活性が変わる。上書き確認が出る |
| P1-8 | 名前入力画面 | 1〜12文字、前後空白除去、空文字不可。決定で初期セーブ生成 |
| P1-9 | ワールドマップ（6地点固定表示） | 現在地・解放済み・クリア済み・未解放が色以外でも区別できる |
| P1-10 | STAGE 1 学習画面 | 1画面1メッセージ、進捗表示、**最後まで進んだ時点で**完了 |
| P1-11 | STAGE 1 取組画面 | 選択肢の正誤演出と解説、同一問題の二重加点なし |
| P1-12 | リザルト画面 | 報酬計算と保存が**一度だけ**実行される |
| P1-13 | ルートガード | 未解放ステージ直リンク→マップ、セーブなし→タイトル |

### 5.3 コンテンツ（レーンC）

| ID | タスク | 完了条件 |
|---|---|---|
| P1-14 | STAGE 1のレッスン本文（相撲・力士・土俵・まわし・勝敗・取組） | 小学生が読める分量と表現 |
| P1-15 | STAGE 1のクイズ | 正解が一つだけ存在し、誤答解説が誤解を生まない |

### 完了ゲート（本プロジェクト最大のチェックポイント）

GitHub PagesのURLで、以下が一度も詰まらず通ること。

1. 名前を入力して開始できる
2. マップからSTAGE 1へ入れる
3. 学習を最後まで読み切れる
4. 取組で正解・不正解の双方を体験できる
5. EXPが入り、必要なら番付が上がる
6. **ブラウザを再読み込みしても続きから再開できる**
7. 同じステージを再プレイしてもEXPが二重に入らない

### 注意点

このゲートを曖昧に通すと、以降の全ステージに同じ欠陥が複製される。特に「初回報酬フラグ」と「リザルトの二重実行防止」は、ここで実機確認する。

## 9. テストの投入タイミング

テストは最後にまとめず、以下のタイミングで積む。

| 種類 | 投入時期 | 対象 |
|---|---|---|
| 単体 | Phase 1前半（P1-1〜P1-6と同時） | 番付導出、解放順、初回報酬、セーブ検証、合格率境界 |
| コンポーネント | Phase 1後半〜Phase 2 | 選択肢操作、解説表示、未解放地点の不活性、つづきからの状態 |
| E2E（1本目） | Phase 1完了ゲート前 | 新規開始→STAGE 1クリア |
| E2E（残り） | Phase 3〜4 | 再開、全6ステージ通し、再挑戦、モバイル、サブパス配信 |

E2E1本目をPhase 1の完了条件に含めるのは、Phase 2の汎用化リファクタで壊れたことを即座に検知するため。

## 10. 主要リスクと対応

| リスク | 影響 | 対応 |
|---|---|---|
| GitHub Pagesのサブパスでリンク・画像が壊れる | 公開直前に発覚すると手戻りが広範囲 | Phase 0完了ゲートで本番URL確認を必須化。以降も各フェーズ末に確認 |
| Phase 2の汎用化でSTAGE 1が壊れる | 縦切りの成果を失う | 汎用化の前にE2E1本目を用意する |
| 初回報酬の二重付与 | 番付が不正に上がり、学習の達成感が崩れる | 報酬フラグをPhase 1で実装し、単体テストと実機確認の両方で検証 |
| 相撲コンテンツの誤り | 学習コンテンツとして致命的 | レーンCを先行させ、Phase 4で通し校正。正解が一意であることを機械検証（P2-12） |
| ピクセル素材の遅延 | 実装が待ち状態になる | 単色矩形のプレースホルダで実装を先行し、後から差し替える |
| localStorageが使えない環境 | プレイ不能と誤認される | 保存失敗を検知してもプレイは継続させ、未保存を明示（P4-7） |
| スコープ拡大（自由移動、音、82手など） | MVP未完のまま長期化 | PRD「14. MVPスコープ／含めないもの」を判断基準として据え置く |

## 11. スコープ判断の基準

以下は**MVPに含めない**。実装中に要望が出た場合も、Phase 4完了までは着手しない。

- ユーザー登録、サーバー、データベース
- マルチプレイ、ランキング、課金
- 自由移動を伴う本格RPG、複雑な戦闘システム
- リアルタイムの大相撲情報
- 音響演出（ON/OFF付きで将来追加）
- 決まり手82手、歴史編・文化編、デイリークイズ、称号・実績

## 12. 数値パラメータの扱い

EXP配分、番付の必要累積EXP、合格率は**設計書時点では仮の値**である。ハードコードせず、以下の方針で扱う。

- 合格率：ステージデータ（`Stage.passRate`）に持たせる
- EXP：レッスン・クイズ・ステージ各データの `rewardExp` / `clearRewardExp` に持たせる
- 番付の必要EXP：`src/data/ranks.ts` に集約する

Phase 3完了時点で通しプレイを行い、**昇進テンポとプレイ時間を見て調整する**。この調整はコード変更を伴わないことを、Phase 2完了ゲートで担保しておく。

## 13. 着手順の要約

```text
1. Phase 0を終わらせ、まず「本番URLで表示される」状態を作る
2. Phase 1でSTAGE 1だけを端から端まで完成させ、再読み込み再開まで実機で確認する
3. Phase 2で汎用化してから、STAGE 2〜5をデータで追加する
4. Phase 3で最終試験と横綱昇進、エンディングを繋ぐ
5. Phase 4でアクセシビリティ、エラー復旧、テスト、コンテンツ校正を仕上げる
```

最も重要なのは2である。ここを完成させずに3以降へ進むと、欠陥が全ステージへ複製される。
