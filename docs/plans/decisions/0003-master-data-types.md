# ADR-0003: マスターデータの型を4件追加する

状態: 採用
日付: 2026-08-29

## 背景

[設計書](../../sumo-quest-design.md)「9. コンテンツデータ」は `src/data/` に7ファイルを置くことを求めている。

```text
stages.ts / lessons.ts / quizzes.ts / techniques.ts / terms.ts / ranks.ts / npcs.ts
```

一方、同じ設計書の「8. データモデル」が型を定義しているのは前半の3つだけである。

`techniques.ts` / `terms.ts` / `ranks.ts` / `npcs.ts` に対応する型が存在しない。

[P0-6](../phase-0-foundation.md)（`src/data/` 配下7ファイルを型付きで用意する）は、この4件がないと完了できない。

## 決定

`src/types/game.ts` に次の4つの型を追加する。

| 型 | 対応するファイル |
|---|---|
| `Technique` | `techniques.ts` |
| `Term` | `terms.ts` |
| `Npc` | `npcs.ts` |
| `Rank` | `ranks.ts` |

設計書「8. データモデル」は書き換えない。
[CONVENTIONS.md](../CONVENTIONS.md)「決定は追記のみで記録する」に従い、本ADRを追加する。

各型の定義は `src/types/game.ts` を正とする。
**本書にフィールドを転記しない。**
転記すると、片方だけ更新されて食い違う。

## 理由

`Technique` と `Term` に説明文を持たせるのは、設計書「6.7 技図鑑・用語辞典」が
「図鑑の情報は学習データと同じマスターデータを参照し、説明の重複管理を避ける」と定めているため。
説明を学習データ側に置くと、この要求を満たせない。

`Rank` に `requiredExperience` を持たせるのは、
[scope.md](../scope.md)「数値パラメータの扱い」が必要累積EXPの保持場所を `src/data/ranks.ts` と定めているため。

`Rank.requiresFinalExam` を設けるのは、設計書「7. ゲーム進行ルール」で
横綱だけがEXPではなく最終試験クリアを条件とするため。
横綱を特別扱いする判定をコードに直接書くと、番付の追加や調整がコード変更を伴うことになる。

`Npc.portraitPath` を `public/images/characters/` 配下の相対パスとするのは、
`basePath` の解決をデータではなくパスヘルパー（P0-9）に集約するため。
データに絶対パスを持たせると、サブパス配信（[R-1](../risks.md)）の解決箇所が分散する。

## 影響

- `src/types/game.ts` に4つの型が増える
- `src/data/` の7ファイルがすべて型付きで成立する
- 設計書「8. データモデル」は、これら4件について本ADRを参照して読む必要がある

## 検討した代替案

### 設計書「8. データモデル」を直接書き換える

1箇所で読めるようになる利点はある。
しかしCONVENTIONSが設計書の直接編集を避ける方針を定めており、
並行作業中の設計書への書き込みは衝突の原因になるため採らない。

### 型を置かず、データファイル側で構造を推論させる

`as const` で書けば型注釈なしでも成立する。
しかしP0-6の完了条件が「型付きで存在する」ことであり、
参照側（図鑑・辞典）が期待する構造を明示できないため採らない。

### 番付の必要EXPをコード（`lib/ranks.ts`）に持つ

判定ロジックと値が近くなる利点はある。
しかしscope.mdが保持場所を `src/data/ranks.ts` と定めており、
Phase 3での数値調整がコード変更を伴わないことをPhase 2の完了ゲートで担保する方針に反する。
