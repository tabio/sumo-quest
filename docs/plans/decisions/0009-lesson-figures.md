# ADR-0009: 学習の画面に図を差し込む

状態: 採用
日付: 2026-08-29

## 背景

学習パートは1画面1メッセージの文章だけで構成されている。

設計書「6.4 学習」が挙げる画面要素も、NPCの立ち絵と会話ウィンドウであり、
本文の中に図を置く想定がない。

しかし学習の中身には、文章だけでは像を結びにくいものが含まれている。

- 位置関係（土俵の円と俵、まわしを締める位置、上手と下手の腕の内外）
- 動きの向き（寄り切りと押し出しの違い、叩き込みで力が向かう先）
- 順序と量（番付10段の並び、15日間の勝ち越し、1年6場所、1日の流れ）

いずれも一度図で見れば済むが、文章で説明すると長くなり、読み手の負担が増える。
これはPRD「2. 背景」が避けようとしている「文章中心で学習の負担を感じやすい」状態そのものである。

一方、ドット絵素材は揃っていない（R-5）。
NPCの立ち絵も現状はプレースホルダを指している。

## 決定

**学習のメッセージ単位で図を差し込めるようにし、図はインラインSVGのコンポーネントとして実装する。**

### データ

`Lesson.messages` の要素を文字列から `LessonMessage` に変える。

```ts
export type LessonMessage = {
  text: string;
  figureId?: LessonFigureId;
};
```

図は画面（メッセージ）に付ける。位置指定（何番目のメッセージか）では持たない。

### 図の実体

図は `src/components/learning/figures/` のReactコンポーネントで、インラインSVGとして描く。

`LessonFigureId` は `src/types/game.ts` の `LESSON_FIGURE_IDS` から導き、
描画側の対応表を `Record<LessonFigureId, ...>` とする。

図の見出しと読み上げ用の説明は、データではなく図の側が持つ。

## 理由

### なぜ画像ファイルではなくインラインSVGか

- 素材の到着を待たずに実装できる（R-5）。図の内容がコードとして残るため、後から直せる
- 色をデザイントークンから参照でき、配色を変えたときに図だけ取り残されない（ADR-0007）
- 拡大しても劣化しない。320px幅から広い画面まで同じ資産で足りる
- 追加の配信物が増えず、`basePath` の解決経路も増えない（R-1）

### なぜ図IDを型で持ち、実行時に検証しないか

コンテンツ検証（`src/lib/contentIntegrity.ts`）はビルド前チェックからNodeで直接呼ばれるため、
パスエイリアスを伴う実行時importを持てない。

`Record<LessonFigureId, ...>` にすれば、対応する図がない参照も、
使われない図の登録漏れも型検査で落ちる。実行時の検証は重ねない。

### なぜメッセージを常にオブジェクトにするか

`string | { text: string }` の共用体にすると、文章を取り出す箇所ごとに分岐が要る。
分岐は画面側とコンテンツ検証側の2箇所に分かれ、同じ判断が2箇所に散る。

表現をひとつに保ち、図のない画面は `figureId` を省略する形に統一する。

## 影響

- `src/types/game.ts`：`LessonMessage`、`LessonFigureId`、`LESSON_FIGURE_IDS` を追加
- `src/data/lessons.ts`：全メッセージが `{ text }` の形になる
- `src/lib/contentIntegrity.ts`：空メッセージの判定が `message.text` を見る
- 設計書「6.4 学習」の画面要素に「図」が加わる。設計書は書き換えず、本ADRを正とする
- 代替テキストの方針（P4-8）は変えない。図は情報画像として扱い、説明を付ける

## 検討した代替案

**写真やイラスト素材を配置する。**
権利の確認が必要で、レトロRPG風の統一感も保ちにくい。素材が揃うまで実装が止まる。

**図をメッセージの位置（何番目か）で指定する。**
メッセージを1行足すだけで図の位置がずれる。
ずれても機械的には検知できず、`docs/plans/CONVENTIONS.md`「安定IDで参照する」の考え方にも反する。

**技図鑑にだけ図を置く。**
学習で分からなかった読み手が、図鑑を開き直す必要がある。
図が要るのは、その説明を読んでいる瞬間である。
