# ADR-0004: 報酬計算を取組の終了時に行い、リザルトは表示に専念する

状態: 採用
日付: 2026-08-29

## 背景

[設計書](../../sumo-quest-design.md)「6.6 リザルト」は、リザルト画面について
「報酬計算と保存を一度だけ行う」と定めている。

リザルト画面が表示する必要があるのは次の項目である。

- 正答数
- 獲得EXP
- 新しく習得した技・用語
- 昇進前後の番付
- 次ステージ解放通知

このうち獲得EXPと昇進前後の番付は、**取組の前後を比べないと出せない**。

一方、本プロジェクトはサーバーを持たず、リザルトは `/result/[stageId]` という
独立したURLである。
利用者が再読み込みしたり、URLを直接開いたりできる。

リザルト画面の描画時に報酬計算を行う設計にすると、次の問題が生じる。

- 再読み込みのたびに計算が走り、EXPが増えうる（[R-3](../risks.md)）
- 「一度だけ」を担保するために、画面側でフラグ管理を作り込むことになる
- そのフラグはステージごとに必要で、ステージが増えるたびに複製される

## 決定

**報酬計算は取組の終了時点で行う。** リザルト画面は表示だけを担当する。

- Reducer に `FINISH_BATTLE` アクションを追加する
- 取組の最終問題を終えた時点で、取組画面がこれを1回送る
- `FINISH_BATTLE` は、結果の記録・合否判定・合格時のクリア処理をまとめて行い、
  表示に必要な差分を `lastBattle` として状態に持つ
- `lastBattle` は**セーブに保存しない**。再読み込みで失われてよい
- リザルト画面は `lastBattle` を読むだけで、`dispatch` を行わない
- `lastBattle` がない状態でリザルトURLを開いた場合は、マップへの導線を出す

設計書「10. 状態管理」が挙げる8アクションは変更しない。`FINISH_BATTLE` はその追加である。

## 理由

リザルト画面から副作用を無くすと、「一度だけ実行される」がフラグ管理ではなく
**構造として満たされる**。画面が計算しないので、何度描画しても増えない。

`lastBattle` をセーブに保存しないのは、これが進行ではなく直前の出来事の説明だからである。
保存すると、次にどこで消すかという判断が新たに必要になる。
再読み込みで失われても、進行そのもの（EXP・番付・ステージ状態）はセーブに入っており損なわれない。

`FINISH_BATTLE` を1つのアクションにまとめたのは、
記録・合否判定・クリアを別々に送ると、その順序と組み合わせが画面側の責務になるためである。
順序を間違えると報酬が二重に入りうる。

## 影響

- `GameState` に `lastBattle` が増える
- リザルト画面（P1-12）は `dispatch` を持たない
- 取組画面を離れて再度リザルトURLを開いても、EXPは増えない
- リザルトを再読み込みすると内容は失われ、マップへの導線だけが残る

## 検討した代替案

### リザルト画面で計算し、実行済みフラグを持つ

設計書の記述にはこちらが近い。
しかし「一度だけ」を画面側の状態管理で守ることになり、
ステージが増えるたびに同じ仕組みを複製する。
[R-3](../risks.md) の対策としては、構造で防ぐほうが確実である。

### 結果をクエリパラメータでリザルトへ渡す

URLだけで完結し、再読み込みにも耐える。
しかし正答数やEXPをURLに載せると、書き換えるだけで報酬を操作できる。
学習の達成感を壊すため採らない。

### 結果を localStorage の別キーに保存する

再読み込みに耐えられる。
しかし保存先が増え、いつ消すかの判断が必要になる。
リザルトは一度見れば足りる情報であり、そこまでの永続性を必要としない。
