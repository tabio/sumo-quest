# ドキュメント運用規約

本ディレクトリの文書を、複数人が並行して更新してもコンフリクトが起きにくい状態に保つための規約。

対象は `docs/` 配下すべて。

## 前提：2種類のコンフリクト

| 種類 | 例 | 検知 |
|---|---|---|
| 行の衝突 | 同じ行を2人が別々に書き換える | Gitが検知する |
| 意味的な不整合 | 同じ数値が2箇所にあり、片方だけ更新される | **検知されない** |

後者はマージが成功してしまうため、レビューで見つからなければそのまま残る。
以下の規約は、前者を減らすことと後者を構造的に発生させないことの両方を狙う。

## 規約

### 1ファイル1オーナー

フェーズごとにファイルを分け、同時に書き込む人を原則1人にする。

各フェーズファイルの冒頭に `オーナー` を明記する。
オーナー以外がそのファイルを変更する場合は、事前にオーナーへ知らせる。

### 進捗を中央に集約しない

全体の進捗表をREADMEに置かない。
進捗はフェーズごとのファイル内の状態欄でのみ管理する。

中央の進捗表は、全員が毎回書き換える最大のホットスポットになる。
「全体状況を1箇所で見たい」という要求は、ドキュメントではなくPRとIssueで満たす。

### 見出しに番号を振らない

`## 4. Phase 0` のような番号付き見出しは、節をひとつ挿入すると以降がすべてずれ、
無関係な変更どうしが衝突する。

新規に書く文書では見出し番号を使わない。
相互参照は見出しテキストとファイル名で行う。

> 既存の `sumo-quest-prd.md` と `sumo-quest-design.md` は番号付きのまま凍結する。
> 番号の振り直しは全行を書き換えることになり、かえって危険なため。

### 安定IDで参照する

相互参照には、位置に依存しない永続IDを使う。

| 種類 | ID形式 | 例 |
|---|---|---|
| タスク | `P<フェーズ>-<連番>` | `P1-3` |
| リスク | `R-<連番>` | `R-2` |
| 決定 | `ADR-<4桁>` | `ADR-0001` |

**IDは一度振ったら変更しない。** 欠番が出ても詰めない。
不要になったタスクは行を削除せず、状態を `取消` にして残す。
行の削除は、その行を参照していた他文書のリンクを黙って壊す。

### 表は末尾に追記する

タスク表・リスク表の行を並べ替えない。
新しい行は必ず末尾に足す。

行の挿入や並べ替えは、他の人の追記と同じ位置で衝突する。
末尾追記なら、Gitは多くの場合そのままマージできる。

### 1文1行で書く

段落を1行にまとめず、文の区切りで改行する。

同じ段落の別々の文を2人が直した場合、1行なら必ず衝突し、
文ごとに行が分かれていれば自動マージされる。

表示上は連続した段落として描画されるため、読み手への影響はない。

### 同じ事実を2箇所に書かない

数値・条件・判断基準は、必ず1箇所を正とし、他からは参照する。

| 事実 | 正とする場所 |
|---|---|
| 設計判断・データモデル | `../sumo-quest-design.md` |
| プロダクト要件・スコープ | `../sumo-quest-prd.md` |
| 実行順序・完了条件 | 各フェーズファイル |
| MVP境界・数値パラメータの扱い | `scope.md` |
| リスクと対応 | `risks.md` |
| テストの投入時期 | `testing.md` |

転記したくなったら、代わりにリンクする。
転記は、意味的な不整合を生む最大の原因である。

### 決定は追記のみで記録する

設計書やPRDを書き換えたくなった場合、原則としてそれらを直接編集せず、
`decisions/` に新しいADRファイルを1件追加する。

- ファイル名：`NNNN-短い説明.md`（例：`0001-split-execution-plan.md`）
- 1決定1ファイル
- 既存のADRは編集しない。覆す場合は新しいADRを追加し、旧ADRを `置換済み` とする

**`decisions/` に索引ファイルを置かない。**
索引は全員が追記するホットスポットになるうえ、ファイル一覧がそのまま索引として機能するため不要。

### 追記専用ファイルの自動マージ

`risks.md` は行の追記しか行わないため、`.gitattributes` で `merge=union` を指定している。
双方の追加行が両方とも残る。

この指定は追記専用のファイルにのみ有効である。
行の順序や一意性が意味を持つファイルに適用してはならない。
重複行が生まれても機械的には検知されない。

### PRを小さく保つ

ドキュメント変更は実装変更と分け、単独ですぐマージする。

長く生きているブランチほど、他の変更と離れてコンフリクトの確率が上がる。
「あとでまとめて直す」を作らない。

## 新しいフェーズ文書を追加する場合

既存のフェーズファイルの構成を踏襲する。

```text
# Phase N: 名前

オーナー: （氏名）
前提: （着手前に通過している必要のあるゲート）

## 目的
## タスク        ← ID・タスク・完了条件・状態の表
## 完了ゲート    ← チェックリスト
## 注意点
## 関連          ← 参照するリスクID、テスト、決定
```

構成を揃えると、同じ位置に同じ種類の変更が入るため、差分が読みやすくなる。
